## 〇、名单是怎么算出来的（不是数出来的）

`run.mjs` 只按名字 import 一部分文件，但**被 import 的夹具**（`b05c-harness` / `b05d-fixture` / `html-dom` / `kw-fixtures` / `page-source` …）也会跟着跑。所以判定用**可达性**而不是「有没有出现在 run.mjs 里」：

```
从 run.mjs 出发，沿 `from './x.mjs'` 做 BFS，在 tests/ 内部递归
  184 个 .mjs  →  可达 161  →  不可达 23
```

**和 lead 数的 25 的差别（口径差，不是谁数错了）**：

| 怎么数 | 数出 | 差在哪 |
|---|---|---|
| 「文件名没出现在 `run.mjs` 里」 | **28**（+ `run.mjs` 自己是 29） | 把 **5 份夹具**也算成孤儿：`b05c-harness` / `b05d-fixture` / `html-dom` / `kw-fixtures` / `page-source` —— 它们**每次全量都在跑**，只是被别的测试文件 import，不是被 `run.mjs` 直接 import |
| **可达性（本报告）** | **23** | 从 `run.mjs` 出发沿 `from './*.mjs'` 递归，能到达的一律不算孤儿 |

所以 **28 − 5 = 23**。lead 数到 25，差额大概是「`make-*` / `wb-focus` 这类要不要算进来」的口径选择：本报告把它们**算进 23 并各自给了处置**（生成器/驱动器，结论都是「不接」），所以无论按哪种口径，**真正要接的仍然是那 15 份**。

## 二、`t52` 那条红的诊断：**红在写死的过期常量，不是代码变了**

```js
check('① schema v62：非破坏 ALTER 三列 + 两个索引', () => {
  equal(SCHEMA_VERSION, 62, 'SCHEMA_VERSION: ')            // ← 只有这一行在红
  const migration = MIGRATIONS.find(item => item.version === 62)
  … 断言 v62 的 SQL 里有 3 条 ALTER + 2 个索引 …            // ← 这几行今天仍然全绿
})
```

实测：`SCHEMA_VERSION: expected 62, got 68`，且**同一条 check 里后面那些 SQL 断言根本没机会执行**（`equal` 先抛）。另外 3 条 check（导入入库 / ASIN 列表 / 店铺筛选）**全绿**。

所以它不是「死掉的套件」，是**「钉住了当时那个版本号」**。这两种要分清：

| | 现象 | 处置 |
|---|---|---|
| 行为被取代 | 断言测的东西今天已经不该那样 | **退役**（改断言就是粉饰） |
| **常量写死** | 断言测的东西还在，只是「当前版本 = 62」过期了 | **改断言**（把「等于 62」换成「≥ 62 且 v62 迁移在位」），行为断言一条不动 |

`t52` 是第二种。**最小改法（一行，且不弱化）**：`equal(SCHEMA_VERSION, 62)` → `if (SCHEMA_VERSION < 62) throw new Error(...)`，并在同一条 check 里补一句 `applied.includes(62)`（迁移真的跑到过）。这样它从「钉死当前版本」变成「钉住这条迁移曾经存在并已应用」——**后者才是它当初想测的东西**。

**对照：本次没有发现「行为已被取代」的套件。** 5 份探针里只有 `probe-optimize` 是「跟的行为变了」（报告可能为空），但它是探针、不是套件，所以结论是**删**而不是**改**。这一点按 lead 的要求单独验过：**没有一份真套件需要靠改断言来变绿。**
