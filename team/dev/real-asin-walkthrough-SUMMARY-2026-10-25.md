## 八、第 7 轮：想补第 1 门，发现**这条路 agent 走不了**（R-10）

### 想做什么
把 4 个 ASIN 归到一个店铺，看第 1 门「对象明确」能否也变绿（九门 5/4 → 6/3）。

### 卡在哪
查 `shop` 表：**只有 1 行，而且是已归档的测试残留**
（`QA-T47-6173-EDIT`，2026-10-22 归档）。**没有在用的店铺。**

于是查有没有建店铺的路径：
```
index.js 里 shop 相关工具：0 命中          ← TOOLS 里没有任何店铺工具
routes.js 里：shop-save / shop-archive / shop-restore   ← 只有页面写路由
```

**结论：店铺只能从页面建，agent 建不了。**

### 为什么这是 P1，不是 P2
优化九门的第 1 门要求「店铺归属」，而**整个优化流程是 agent 驱动的**：
`amzn_optimize_precheck` 的补数清单写着
> 「配置：在设置页给这个 ASIN 记归属：店铺 / 品牌 / 产品线（amzn_workbench_context）」

`amzn_workbench_context` 是**读**工具（读页面当前选中什么），它不能建店铺。
所以这条建议指向一条**agent 用不了的路** ——
结果就是**第 1 门对 agent 永远是降级**，无论它多努力。

### 它和 R-9 是同一类的两个方向
- **R-9**：工具指着一条**无效**的路（写缓存，看起来成功其实没生效）；
- **R-10**：工具指着一条**存在但调用方走不了**的路（页面能建、agent 建不了）。

两者都是「**说得到的，做不到**」。F-7 的原则是「页面能做的事，工具就该能做」——
这条正好落在那条原则的缺口上。

### 修法（下一轮做，本轮不半成品落地）
补 `amzn_shop_upsert`（建 / 改 / 归档），照 `amzn_product_line_upsert` 与
`amzn_workspace_upsert` 的模式；注册面 5 处（TOOLS / buildTools / facades / audit targets / t33 数字），
并加测试。**不在本轮硬塞一个半成品进树**——今天已经因为「改了但没留下」栽过两次。

### 这一屏是本仓诚实度的最高水平
```
数据前置检查：窗口内**一类数据都没有** —— 这不是「没有变化」，是还没有人看过。
  ✗ 会话与订单：**本插件没有这条通道** —— 没有任何通道。
    业务报告（Business Report）的表单格式没有对应的解析器，kw_import 的六类识别里也没有它
    —— 而「会话数」这个字段在本仓的任何一张表里都不存在。
    把它列进补数清单会让人去找一个不存在的导入入口。
  ✗ 退货/差评主题：**本插件没有这条通道** —— …差评正文已经在库里，
    但本仓没有主题词表、也没有分类器，所以「主题」这个聚合量仍算不出来。
回滚建议：不可以 —— 最后一个观测节点还没有结论 —— 没有结论就谈不上「无改善」。
```
**「没看过」「没通道」「看了但没有」三件事，在这屏上是分开的。**
而且它拒绝把「没有通道」写进补数清单 —— 因为那会让人去找一个不存在的导入入口。
（这与本批 R-9 的教训正好同向：**说得到的必须做得到**。）

### P3（未修，记下来）：观测窗口印出「30 秒」，读者会以为算错了
```
窗口 2026-10-25T08:12:40.876Z → 2026-10-25T08:13:10.509Z   ← 30 秒
```
原因是窗口是 `[观测起点, 现在]`，而刚登记完就查，所以只有 30 秒。
**逻辑没错，读起来像算错。** 可修的写法：节点都没到期时，窗口那一行改成
「窗口一开始，到现在 30 秒 —— 三个节点都还没到期」，把「短」解释掉，
而不是让读者自己怀疑。

## 十一、第 27 轮：搜索量读错表是**系统性的**，不是一个点

第 26 轮修了 precheck 那一处（R-20）。为了防第四个读端，写了守门 `tests/t94-search-volume-table.mjs`：
扫 `src/**/*.js` 里**同一条 SQL** 同时出现 `FROM keyword` 与 `search_volume` 的地方，报红。

**它一上线就抓出 4 处**：

| 文件 | 是什么 | 状态 |
|---|---|---|
| `domain/search/index.js` | 搜索框「按搜索量从高到低排」 | ✅ **本轮已修** |
| `store/kw.js` | 关键词列表（两处） | ⬜ 待修 |
| `store/queries.js` | 关键词关联查询 | ⬜ 待修 |

**为什么是真 bug**：`keyword` 表的 `search_volume` **16 行全是 NULL**（实测）。
所以 `ORDER BY search_volume DESC NULLS LAST` **等价于不排序** ——
读者看到的顺序看起来「有排序」，只是那个顺序没意义。**这比报错更难发现。**

**本轮只修了搜索框那一处**（用户直接会用到）。剩下 3 处没修完，所以：

> **t94 已写好但【不接线】** —— 它还红着（3 处违规）。
> 红着接进主套件会让全量变红；把它改成「只报告不失败」等于把守门变装饰。
> **下轮把 3 处修完再接线。中间状态如实留在这里，不假装已修。**

### 三张表各自的职责（写下来，供下一个人查）
| 表 | 行数 | 回答什么 |
|---|---:|---|
| `kw_master` | 30,778 | 这个（词,站点）在**市场上**的搜索量与广告表现 |
| legacy `keyword` | 16 | 这个 ASIN **有哪些候选词**（历史入口；搜索量列全空） |
| `asin_keyword` | 8 | **我们在这个词上测到了第几名**（测量结果） |

**三者不是同一件事，数字不同不是错；错的是拿一张表的列去回答另一张表的问题。**
