# 守门自身体检 · 2026-10-25

> **为什么需要这份**：一个不会红的守门，和没有守门是一样的；
> 而一个**误报**的守门更危险 —— 它会让人去改一段本来正确的代码（R-21 就是这么发生的）。
> 唯一能证明守门不是装饰的方法：**把被测实现故意弄坏一次，看它红不红。**

## 一、纪律（做破坏性验证的前提）

1. **工作区必须干净**（`git status --porcelain -- src/ tests/` 为空）——否则恢复会丢别人的改动；
2. 每条只改**一处**，改前 `Copy-Item` 备份到 `%TEMP%`；
3. 跑完立刻还原，**并核对 `git status` 为干净**；
4. 一次只验一条，不批量 —— 批量改坏之后分不清是哪条红的。

## 二、本轮验的两条（各代表一类）

### ① `t87` 行为守门 —— 空值不许把列塌陷

**弄坏什么**：`src/tools/render.js` 的 `const EMPTY_CELL = '—'` → `''`（= R-3 修复前的样子）

```
弄坏后:  T87: 2 passed / 4 failed      ← 4 条红，不是 1 条
恢复后:  T87: 6 passed / 0 failed
文件与 git 一致: ✅
```

**结论**：它会红，而且红得**比你弄坏的地方多**（一处改动触发 4 条断言）——
说明这组断言互相独立，不是同一条抄了四遍。

### ② `t94` 源码守门 —— 不许拿空列当 `ORDER BY` 依据

**弄坏什么**：`src/domain/search/index.js` 的
`ORDER BY COALESCE(m.search_volume, k.search_volume)` → `ORDER BY k.search_volume`，
并去掉 `LEFT JOIN kw_master`（= R-21 修复前）

```
弄坏后:  T94: 3 passed / 1 failed
         domain\search\index.js        ← 不只红，还**点名**了文件
恢复后:  T94: 4 passed / 0 failed
文件与 git 一致: ✅
```

**结论**：它会红，并且**说出是哪个文件** —— 源码守门的价值全在这一点上，
只说「有违规」而不说在哪，下一个人还得自己找一遍。

           旧控件名还没清零：

## 六、这次体检暴露了 `t86-⑨` 本身的一个设计问题（**未改，先记下**）

**它是被一行注释打红的。**

我加的不是代码，是**注释**：

```js
// 这里的旧文案是：页面还没有开跑按钮
```

而这条守门扫的是**整个文件文本**，没有剥注释。于是：

- **好处**：严格 —— 连注释里都不许出现旧名，搜索代码的人不会被误导；
- **坏处**：**注释里解释「为什么删掉它」是一种正当需求**，而守门会让这种注释必须被删掉。
  今天我自己就在注释里复述过旧文案，被打红过两次（D-4 / T92-④）。

**两种处理都说得通，所以我没有擅自改它**：
- 若定为「注释也不许」→ 现在是**有意的严格**，只需在守门的说明里写明「想解释历史请换个说法」；
- 若定为「只禁代码」→ 加一层剥注释（`t94` 就是这么做的：`codeOnly()`）。

**我倾向后者**：守门的职责是「不许再指向那个控件」，而注释里的名字**不会被执行**；
误报的守门会被关掉，这比多一条宽松规则危险得多。

留待下一轮定夺，并写进 t86 的说明。

## 八、第三批：把 `t86-⑨` 改成只扫代码（落实第六节那个倾向）

**改动**：`tests/t86-optimize-run.mjs` 第 469 行附近
`const text = readFileSync(file, 'utf8')` → `const text = codeOnly(readFileSync(file, 'utf8'))`
（`codeOnly` 与 ⑧ 同一个实现，早就在这个文件里）。

**为什么**：
- 守门的职责是「不许再**指向**那个控件」，**注释里的名字不会被执行**；
- **误报的守门会被关掉** —— 那比多一条宽松规则危险得多（R-21 就是这么误伤了两处正确代码）。

**代价（如实说）**：注释里可以出现旧名，于是「搜代码时被注释误导」的可能还在。
**这条守门管不到它** —— 那是写注释时该自律的事，不该靠一条扫全文件的判据去管。

### 三重验证（这一次是「精确性」验证，不是「会不会红」）

```
正常跑                        T86: 9 passed / 0 failed
注释里加旧名                  9 passed / 0 failed   ← **不红**（新行为）
代码里加旧名                  8 passed / 1 failed   ← **红**（守门仍然有效）
                               旧控件名还没清零
render.js 与 git 一致          ✅
```

**光证明「会红」不够，还要证明「不该红的时候不红」。**
一个只会红的守门和一个永远绿的守门一样没用 —— 前者会逼人删掉正确的代码。

## 九、四批合计

| 守门 | 类型 | 弄坏 | 结果 | 判据精确吗 |
|---|---|---|---|---|
| t87 | 行为 | 空值占位 → 空串 | 4 条红 | — |
| t94 | 源码 | ORDER BY 空列 | 1 条红 + 点名文件 | ✅ |
| t86-⑨（旧） | 防回归 | 注释里加旧名 | 1 条红 | ❌ **误报** |
| t86-⑨（新） | 防回归 | 注释加旧名 / 代码加旧名 | **不红 / 红** | ✅ **精确** |

**这一格「误报 → 精确」是四批体检里最重要的结果**：
它说明体检**不只该问「会不会红」，还该问「什么时候不该红」**。
