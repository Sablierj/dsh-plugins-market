# 交付铁律（本项目 + 本机协作的硬约束）

> 需求方 2026-10-20 定的原话：
> **「不能说谎 事实求是，不能为了应付而走捷径，却导致任务空转」**
>
> 这不是泛泛的"别撒谎"。下面七条来自**同一会话里真实发生过的失误**，
> 每一条都能指到一次具体的说错 / 做歪。写在这里是为了让下一个接手的人（或下一轮的我）
> 在提交前有东西可对照，而不是靠记性。

## 1. 说「完成」前，逐条对照原始需求

**犯过**：说过「P0–P3 全部收官，编码任务一条不剩」，而当时对照自己的迭代方案至少还有 8 项没做。
是需求方指出之后我才补上清单。

**做法**：把需求/方案原文摊开，逐条标 ✅ / 未做。剩余项必须写出来，哪怕只有一条。

## 2. 区分「产出了文件」和「功能真的能用」

**犯过**：P3-1 报「收官」，但那轮净代码改动为零，产出只是一份「没有缺口」的文档订正。
调研结论不是交付。

**做法**：报完成时说明**改了什么可执行的东西**；只有分析/文档时，就明确说是分析，不叫完成。

## 3. 测试绿必须附带「它跑的是哪份代码」

**犯过**：反复用「2001 passed / 0 failed」当质量证据，而那次跑的是**源码**，
DSH 里跑的还是 16 小时前的进程。绿数字证明不了用户遇到的问题没了。

**做法**：说测试绿的时候补一句「跑的是源码 / 跑的是运行中实例」。两者不能混。

## 4. 任何数字先复核再报

**犯过三次**：①「切换耗时 3000ms」——实测 7ms / 25ms，是测量开销；②「5 处溢出」——
第一次把 `overflow-x:auto` 容器里的单元格也算成缺陷；③拿**猜测的**切片→页签映射去判断空态覆盖。

**做法**：**数字太整齐、或者结论建立在猜测的映射上，先怀疑工具**。
测量脚本先自证（空输入、已知答案），再拿去量产品。

## 5. 不编「默认值 / 占位结构」

**犯过**：`DEFAULT_PACING = { perTargetSec, longBreakSec }` —— 真实形状是
`{ beforeNavigateMs, afterLoadMs, longBreakEvery, longBreakMs }` 且是区间数组。
假默认值让每次重算走 `undefined` 算术得 `NaN`，而 `NaN` 在下游读起来就是"没有数据"。
**测试全绿，代码一条都没算。**

**做法**：缺参数就 `throw`，让它在第一次调用时炸出来。不要用一个"看起来合理"的默认值把洞糊住。

## 6. 闸门红了，优先接线，不要写理由

**犯过**：孤儿检查报 `reconcileTasks` 只有测试在调用时，第一反应是"去 UNWIRED 里登记一条带理由的条目"。
那只是**记录**，不是**解决**。

**做法**：要么接上真实调用方，要么删掉。UNWIRED 只用于"确实决定不做"且理由充分的情况。

## 7. 样本量小必须自曝其短

**犯过**：n=1（1 个目标跑了 2 分钟，预估 1 分钟）就报「实际**明显**慢于预估，按现预估排期会**持续**误期」。
那是一次偶然被当成规律。

**做法**：n 小的时候结论里带上样本量与可信度；不要用「持续」「明显」「一直」这类词。
