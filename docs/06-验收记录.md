1. **读 amazon-ops（只读）**：`src/sources/amazon-ops.js`，`readOnly` 打开它的库，`SELECT ... FROM listing`；有采集就用它的真文案，没有就返回 `found:false` 并说明原因。**绝不写它的库。**
2. **人工补录**（v5 新表 `sif_listing_asset`）：图片数 / 白底 / ≥1000px / 视频 / A+ / 差评主题。补录后这三项从 `nodata` 变成真实判定。

## 三十、被这条链路暴露的一个设计问题

补录后分数从 64 掉到 0，会被误读成「Listing 变差了」。实际是「之前没看见」。两处修：
- 权重从 high/medium/low = 12/6/3 调成 **8/4/2**，并且**保底 5 分**（全错也不归零）；
- 诊断报告里加一句：「刚补录素材时分数下降是正常的——那不是变差，是把没看过的看清楚了」。

**代价**：新旧分数不可直接比较（46→76 是旧权重，64→84 是新权重），文档里两个数字都保留，避免以后拿错基准。

## 三十七、数据对账（专治静默丢数）

`src/domain/consistency.js` + `GET /api/consistency`：拿原始返回（sif_raw）与摊平表**逐项比数量**——raw 里 10 周，表里就必须 10 行。页面的「数据健康」卡直接显示对账结论。

实测（发现一个真问题）：
```

```
原因：**SIF 的 ABA 返回里有 1 条重复周**（同一日期出现两次）。表按主键去重，所以是 319。

处理：对账改成**按唯一周比**，并在明细里注明「raw 有 1 条重复周，已按唯一周入库」。
修正后：
```
total=5 ok=5 mismatches=0
verdict: 全部 5 项对得上：raw 与表数量一致
  [traffic] B0GV55Q4JG: raw唯一=10 db=10 dup=0 -> ok
  [keywords] B0GV55Q4JG: raw唯一=50 db=50 -> ok
  [aba] bench cushion: raw唯一=319 db=319 dup=1 -> ok（1 条重复周已去重）
```

这条比数字本身更重要：**它证明了「报告里的数=平台返回的数」是可核对的，而不是靠信任。**
