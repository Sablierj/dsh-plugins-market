## 1. O2 · 13 节口径 — **裁决：采用 13 项，A+ 与 视频 分列**（架构师的选择正确）

架构师报告「三份材料互相矛盾」。**我读了原文，结论是它们不矛盾**——是排版把两项挤成了一项：

| 材料 | 原文 | 数出来 |
|---|---|---|
| `amazon-ops-模块设计-v1.0/04-采集中心.md:19-33` | 编号 1–13 的列表，A+ 是第 7 项、视频是第 8 项 | **13 项** ✅ |
| `amazon-ops-需求设计文档-v2.0.md:480` | 「…描述/**A+/视频**/SEO 元信息…」——**斜杠是排版连接符** | 拆开数 = **13 项** ✅ 与上表逐项一致 |
| `prototype/04-collect.html:179-191` | 13 个徽章：`标题 五点 描述 价格 图片 A+ 属性 变体 BSR 评分 后台词 QA 评论` | **另一种东西**，见下 |

**判定**：

1. **采集节的定义取「13 项」**：基础信息 / 五点 / 主图与副图 / 变体结构 / 产品规格与属性 / 产品描述 / A+ / 视频 / SEO 元信息 / BSR 与类目排名 / 评论 / 页面信号 / 关联竞品。**A+ 与 视频 分列**，因为它们各有独立的采集路径与失败模式（A+ 是模块接口，视频是媒体资源），合并会让「视频没采到」被「A+ 采到了」掩盖——正是 §18.3 那句「不能用任务成功掩盖局部缺失」要防的。
2. **原型的 13 个徽章不是节分类，是**「单 ASIN 的紧凑状态条」：它把 `基础信息` 拆成 `标题/价格/评分`，又引入了 `后台词`、`QA` 两个**不在采集节里**的标签。**实现按 13 节渲染**；原型的标签表由 UI 在 B-04 的 UI 交付物里更新为 13 节口径（原型是设计产物，需求是 v2.0 §18.3 + 模块设计 §3）。
3. **不得把 `listing-fields.js:51-63` 的 11 节 `SECTIONS` 当采集节用**——那是优化侧的字段词表，有 `eleven sections` 断言钉住。架构师这条提醒正确，采纳。

## 2. O3 · 「需要登录的字段」 — **裁决：不做节级登录映射**

需求（§18 F04-03）只要求预览里有「风控风险」这一项，**没有给节级登录清单**。

**判定**：**登录态是环境级判定（F04-01 体检项），不是节级属性。** 不发明「哪几节需要登录」的映射——那是把推断写成规格。未登录导致取不到时，**节级状态用 `blocked` 表达**，原因里带登录态，这已经能回答问题，且不新增约定。

## 3. O4 · 代理池 — **裁决：`unknown` + 明示「本版不走代理」，采纳**

原型画了「代理池 18/20」，而本仓 `registry.js:36-39` **没有任何代理字段**。

**判定**：采纳架构师方案——体检第 9 项 `09-proxy` **恒为 `unknown`**，并**明示「本版不走代理」**。这与本仓既有的「声明的不可用而非漏做」一致（如全局搜索的 SKU 一类：声明查不了、不画假数据）。**不许**把 `unknown` 渲染成 `0/20` 或绿勾。
