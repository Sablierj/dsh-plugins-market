# `page.js` 拆分映射表（P1-1）

> 状态：**映射已定稿，试点已完成并验证逐字相同**。剩余 14 块按 §5 的顺序搬。
> 依据：本机实测（2026-10-20，HEAD `c7f4f92` + 本批），不是估算。

## 0. 一句话结论

`page.js` 是**一个模板字符串**，里面装着整页 HTML 和一段约 11,800 行的浏览器脚本。
所以拆分**不需要动代码结构**：把每块原样切成一个「字符串片段」文件，再按**原来的顺序**拼回去，
作用域完全不变（浏览器里仍然只有一个 `<script>`），输出可以做到**逐字节相同**。
试点已经证明这一点（§4）。

**这条很重要**：它意味着 P1-1 是「搬家」，不是「重构」。任何一处顺手改行为，
都会让「输出哈希不等」这条判据失去意义。

## 3. 拆分机制（已跑通）

```
src/web/pages/<module>.js     export const <module>Script = `<原样文本>`
src/web/page.js               import { <module>Script } from './pages/<module>.js'
                              ……模板字符串里用 ${<module>Script} 占位……
```

三条必须守住的细节（都是踩过的）：

1. **片段必须是原文本逐字复制**，包括 `\`` 与 `\${` 的转义。它在原文件里就已经是「模板字符串里的文本」，
   再包一层模板字符串时，那些转义正好还是对的。
2. **片段首行不能多一个换行**：`export const x = \`/* …` 要贴在一起，
   写成 `= \`` 换行再写内容，输出就会多一个 `\n`。
3. **片段尾部不能多一个换行**：结尾写成 `}\`` 而不是 `}\n\``。
   这两条各让输出多了 1 字节，**是靠哈希比对抓出来的**，肉眼看不出。

## 6. 共享层：**先不抽**，等 14 块搬完再抽

`escapeHtml`、`$`、`fmt*` 这些被所有块调用，但它们物理上住在某一块里（例如 `escapeHtml` 在
`prompts` 区）。**这在拆分后依然能用** —— 因为所有片段最终拼回同一个 `<script>` 作用域，
函数声明在同一作用域里会提升。

所以顺序是：

1. 先按块搬（每块一个文件），共享函数**跟着它所在的块走**；
2. 14 块搬完后，再单独做一批「把共享函数收进 `pages/_shared.js`」——
   那时才是真正的结构调整，需要单独一次全量回归。

**不要**在搬块的同时抽共享层：两个动作混在一批里，输出哈希不等时无法判断是哪个引起的。

## 8. 这条映射表证明不了什么

- 它证明的是「可以无损切开」，不是「切开后更好维护」——后者要等拆完再评价。
- 行号是**本批实测**的，任何一次合并都会让它漂；判断块边界请用
  `grep -n "^function render<Module>(" src/web/page.js` 重新量，别抄这张表。
- 15 个块是「历史追加顺序」，不是「依赖顺序」；块之间的调用是双向的（`master` 调
  `research` 的 `renderKeywordDetail`），**拆完不会变成 15 个独立模块**，只是 15 个文件。
