# 数据存放方案（已跑通验证）

> DDL 在 [`schema.sql`](../schema.sql)，冒烟脚本在 [`tools/schema-smoke.mjs`](../tools/schema-smoke.mjs)。
> 已实测：19 张表 + 4 个视图建表通过、`PRAGMA integrity_check = ok`、同周重抓 UPSERT 后行数不变（10→10）。

## 1. 四层数据流（每层职责单一）

```
SIF MCP ──raw JSON──▶ sif_raw          （原样存档，90 天）
                     │
                     ├─摊平─▶ 业务表     （sif_traffic / sif_keyword_aba / sif_asin_keyword …）
                     │                    幂等主键，重抓覆盖
                     ├─规则─▶ sif_insight  （缺口/依赖/悖论/季节窗，可 dismiss）
                     └─生成─▶ sif_report   （markdown，进库可追溯）
                                    │
                              v_* 视图（页面与模型共用同一口径）
```

为什么留 `sif_raw`：SIF 的口径会变（字段改名、`_formatted` 改渲染、点数调价）。摊平表是我对它的**解释**，raw 才是**证据**。没有 raw，口径一改就无法回答「当时那个数是哪来的」。

## 2. 主键与幂等（这是整套设计的地基）

| 表 | 幂等键 | 重抓语义 |
|---|---|---|
| `sif_traffic` | (站点, ASIN, 口径, 周期类型, 周期首日) | 覆盖该周；**不累加** |
| `sif_keyword_aba` | (站点, 词, 周) | 覆盖该周；补历史靠回填 |
| `sif_asin_keyword` | (站点, ASIN, 词, 窗口类型, 窗口值) | 覆盖该窗口 |
| `sif_keyword_demand` | (站点, 词, 统计周) | 覆盖该周 |
| `sif_listing_overview` | (站点, ASIN, 窗口类型, 窗口值) | 覆盖 |
| `sif_ad_campaign` / `sif_ad_group` | (站点, ASIN, campaign/adgroup) | 只更新 first_seen/last_seen，不删 |
| `sif_asin_snapshot` | (站点, ASIN, 抓取时刻) | **追加**（快照就要多份） |

importer 一律写 `INSERT … ON CONFLICT(…) DO UPDATE SET …`。实测：裸 `INSERT` 撞主键会被拒（10 行不变），UPSERT 后仍是 10 行且值被更新——这就是「重跑一百次也不会把数据搞脏」的证据。

## 3. 两个时间轴，别混

| 字段 | 含义 | 用途 |
|---|---|---|
| `fetched_at` | 我什么时候抓的（ISO 时刻） | 审计、缓存命中判断（同一 `params_hash` + 同一天不重抓） |
| `data_date` | 数据本身截止到哪天（`data_notice` 解析） | **所有口径计算必须用它** |

SIF 是 T-1：2026-11-05 抓到的 `data_notice` 写的是 `Data updated through 2026-11-04`。日报标题必须写「截至 11-04」，否则会被当成今天的数据做环比，直接误判「今天暴跌」。

## 4. 粒度总表

| 数据 | 粒度 | 一张表的体量（估） | 保留 |
|---|---|---|---|
| ASIN 画像 | 每次抓取 | 1 行/次 | 全部（增长慢） |
| 流量 | ASIN × 周（日粒度可选） | 52 行/年/ASIN | 周：永久；日：24 个月 |
| Listing 渠道结构 | Listing × 窗口 | 1 行/窗口 | 12 个月 |
| 销量 | ASIN × 月 × 口径 | 12 行/年 | 永久 |
| ABA | 词 × 周 | 52 行/年/词（回填 320 周 ≈ 320 行） | 永久（它就是历史资产） |
| 需求诊断 | 词 × 统计周 | 52 行/年/词 | 24 个月（可由 ABA 重算） |
| ASIN×关键词 | ASIN × 词 × 窗口 | 85 行/ASIN/期 | 24 个月（快照性质） |
| 广告 campaign/ag/词 | 对象 × 周 | 20 campaign × 52 | 24 个月 |
| 竞品 | 词 × ASIN × 抓取时点 | 10-300 行/次 | 12 个月 |
| raw | 每次调用 | 1 行（大 JSON） | 90 天，之后可导出 jsonl.gz |

10 个 ASIN + 500 个词的量级 ≈ 5 万行/年，`sif.db` 预计 30-80 MB，和 amazon-ops（68 MB）同量级，不需要分库。

## 5. 成本：先算点，再动手

实测点数（`sif_catalog` 为准，2026-11-05）：

- **L1 日报** = `ops_get_asin_traffic_trend`(2) + `ops_get_listing_traffic_overview`(3) = **5 点/ASIN·天**
- **L2 周报** = `keyword_signals`(3) + `ad_structure`(2) + `sales_trend`(1) = **6 点/ASIN·周**
- **L3 关键词** = ABA 历史(1/次，最多 10 词) + 需求(2/次，最多 20 词) = **按批计费，不是按词计费**（实测 3 个词共 3 点）
- 场景 `analyze_traffic_anomaly` = 10 点/次，**不进节拍**

按当前密钥（10000 点 / 期，2026-11-05→11-21，共 16 天）预算：

| 配置 | 消耗/期 | 余额留给 |
|---|---|---|
| 10 个 ASIN 全量 L1（16 天）+ L2（2 次） | 800 + 120 = 920 点 | 关键词研究 ≈ 1800 词次 |
| 30 个 ASIN 同上 | 2400 + 360 = 2760 点 | 约 1400 词次 |
| 10 个 ASIN + 200 词 ABA 全量回填 | 920 + 200 = 1120 点 | 首次回填一次性成本很低 |

**结论：这个配额下，「10-30 个主推 ASIN + 200-500 个词」是舒服的规模。** 超过 50 个 ASIN 就该降频（L1 改隔日）或上套餐。

页面上的三道闸：① 调前显示「本次预计 X 点 / 余额 Y」；② 单次超 `日预算`（默认 60 点）直接拒绝；③ 余额 < 15% 时只放行 L1 且黄条提示。

## 6. 缓存与去重（省钱的第一手段）

`params_hash = sha1(tool + 规范化参数)`。
- 命中条件：同 hash 且 `fetched_at` 在 **6 小时内**（SIF 一天一更，日粒度 6 小时足够）→ 直接复用 `sif_raw`，标 `status=skipped(cache)`，**扣 0 点**。
- 用户点「强制刷新」才绕过。
- 好处：一个 ASIN 被 5 次分析反复看，只花第一次的点。

## 7. 口径陷阱（写进 importer 的注释，也写进页面提示）

| 陷阱 | 正确做法 |
|---|---|
| `score` 是「流量分」不是绝对值 | 列名带 `_score`；页面只展示**相对变化**与**占比**，不跨站点横比 |
| `contri_change` 是归因份额 | 文案写「本期波动里 X% 来自这个词」，不写「这个词涨了 X%」 |
| `listingSearch=true` 是父体+子体聚合 | 和单 ASIN 明细**不能相加对账**；存 `scope` 列区分 |
| `search_volume` 在 demand/screen 里是**周**量 | 库里列名不改，但页面必须标「/周」，禁止 ×4 |
| `organic_rank` 形如 `p2,11/48` | 拆三列（页/位/总数）再入库，原始串留 `organic_rank_raw` |
| `null` 与 `0` | 一律存 `NULL`；`sb_score=null` 表示「该周没有 SB 流量」，不是 0 |
| `boughtInPastMonth` 是档位文本 | 原样存 `bought_band`，另解析 `bought_lower` 用于排序 |
| `pagination.poolComplete=false` | 报告必须写「共 N 词，纳入 M 词」，不能说「只有 M 词」 |

## 8. 备份与迁移

- 迁移前自动 `copy amazon-ops.db → data/backups/sif-v{N}-{ts}.db`，保留最近 5 份（学 amazon-ops 的做法）。
- `SCHEMA_VERSION` 单调递增，`MIGRATIONS` 数组只追加不修改——旧库能一路升上来。
- 数据可整体导出：`sif_export year=2026` → `data/exports/sif-2026.csv.gz`（按表分文件），换机时随库拷走即可。
