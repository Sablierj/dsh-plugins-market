# Listing 优化模块 · 建设方案（2026-10-21）

> 作者视角：产品经理 + 亚马逊运营 ｜ 依据：本仓代码现状（真机验证过）+ 外部公开信息（标注为待核验信号）
> 结论先行：**流程要改成「作业单」，不是加功能。**

---

## 0. 一句话

把「优化」从一个**工具箱**改成一个**有前置条件的作业单（Optimize Job）**：
给一个 ASIN，系统自己判断缺什么、能自动补的自动补、不能的明确要人给，
然后冻结证据 → 出策略 → 人确认 → 分字段生成 → 校验 → 人裁决 → 登记发布 → 观察。

现在的 11 个工具都在，缺的是**把它们串起来的那根线**，以及**三个前置数据的自动补齐**。

## 2. 设计：Optimize Job（作业单）

### 2.1 状态机

```
Intake ──▶ Preflight ──▶ Enrich ──▶ Strategy ──▶ Draft ──▶ Validate ──▶ Decide ──▶ Record ──▶ Observe
  给ASIN     判缺什么      自动补齐     人确认      分字段     规则+闸门    人裁决     人工登记     7/14/30天
                              │
                              └─ 补不齐 → 停下，列「谁能补、怎么补」
```

### 2.2 每一步的判据（不能让 Agent 自己"觉得够了"）

| 步 | 判据 | 补不齐时 |
|---|---|---|
| Preflight | 九道门逐门给 `实测/分母` | 产出**缺口清单**，每项带「自动可补 / 需人给 / 本仓没有」三态 |
| Enrich | 只自动做**幂等且无副作用**的：采集、归类、拉库 | 搜索量这种必须有 ABA/广告报表的，**不猜**，标「需人给文件」 |
| Strategy | 九项策略卡（目标用户/差异化/购买疑问/事实边界/关键词优先级/字段分工/保留内容/风险/修改幅度） | 未确认 → **拒绝生成文案**（现在已实现） |
| Draft | 每字段一次生成，带 rationale | 事实缺失 → 标「需人工确认」，不编 |
| Validate | 规则（合法）+ 闸门（做完没）+ Agent 审阅 14 项 | 阻断项必须清零才能提交 |
| Decide | 人：接受 / 修改后接受 / 驳回 | 驳回要留原因，进下一轮 |
| Record | 人工在 Seller Central 发布后登记 | **插件不发布**，只登记 |

### 2.3 关键设计原则（这四条决定成败）

1. **证据信封**：每次 Job 冻结它用过的每份证据（来源表 / 取数时间 / 版本）。
   报告里任何一句话都能回答"你凭什么这么说"。
2. **不伪造**：无来源就说无来源。今天 `review_topics` 与 `Q&A` 在本仓**没有来源**，
   所以「评论痛点」这一类证据只能是 `no-source`，不能由模型"根据常识"编。
3. **不覆盖人工值**：采集补属性只补空缺（今天已实现并有测试）；
   优化草案同样不能静默覆盖人工改过的字段。
4. **默认不动图**：主副图与 A+ 默认**不生成**，要显式开 scope 才做 ——
   因为这两项是品牌资产，且平台侧没有可靠的写回路径。

## 3. 四个缺口的补法

### 缺口 A：竞品自动发现（现在完全靠人工建组）

**建议的三路发现，按可信度排序：**

| 来源 | 怎么来 | 可信度 | 备注 |
|---|---|---|---|
| A1 详情页关联位 | 采集时读 `related_competitors` 节 | 中 | 今天这页是 0 个（定制类没有关联位） |
| A2 类目邻近 | 同子类目 BSR 相邻（如 Patio Furniture Cushions 前后 20 名） | 中高 | 需要能采类目榜；受反爬限制 |
| A3 关键词重叠 | 用本 ASIN 已测词反查「同样排在前列的 ASIN」 | **高** | 已有 `kw_competitor_fact` 与 `amzn_competitor_quadrants` |

**建议默认走 A3**（它最有商业含义：抢同一批词的才是真竞品），A1/A2 作为补充。
产出**候选集**而不是直接建组 —— 人勾选后才建组、才采集。

#### ⛔ 2026-10-21 更新：三路来源**目前都没有数据**（实测）

| 来源 | 实测行数 | 结论 |
|---|---|---|
| A3 `kw_competitor_fact` | **0** | 要卖家精灵 / 西柚（商务未开通） |
| A1 `related_competitors` 节 | 2 个 ASIN 全是 `missing` | 见下 —— 但这很可能是**读不到**，不是页面没有 |
| A2 类目榜 | **没有这张表** | 采集器根本不采类目榜 |
| `competitor_set` | 0 | 从来没人建过 |

**⚠️ A1 的真相：又是"选择器漏了"。** 真机探针发现这一页有 **三组
`[data-cel-widget^="CardInstance"]`** 卡片：

| 卡片标题 | ASIN 数 | 广告? | 能当竞品吗 |
|---|---|---|---|
| Customers who viewed this item also viewed | 6 | 否 | ✅ 行为共视，最强 |
| Featured items you may like | 6 | 否 | ⚠️ 推荐，可能跨类目 |
| Similar brands on Amazon | 5 | **sponsored=true** | ❌ 付过钱的展位，不是对手 |

而提取器找的 `#similarities_feature_div` / `#sp_detail` / `#sp_detail_thematic` /
`#anonCarousel` 在这页上**全部不存在**。所以 `related_competitors = missing` 是
「我们没读」，不是「页面没有」—— 与属性那次是同一类错误。

**因此竞品发现的真实顺序应当是：**

1. **先修 A1 的读取**（不需要任何付费源，改一个选择器的事）——
   并且必须按卡片分组，**排除 sponsored**；
2. 再谈 A3（要等商务开通）；
3. A2 需要新写一个"类目榜采集"，成本最高，暂缓。

#### 修复尝试与回滚（2026-10-21，诚实记录）

我改了一版 `kind: 'related_competitors'` 读取器（按卡片分组、排除广告），
但 `b04-section-writer` 的 4 条断言红：那套夹具是**按选择器字符串查表的假 DOM**
（`'#similarities_feature_div': el()` + 一条复合选择器给 href），
卡片读取器在那里 `querySelectorAll` 拿不到子节点，整节被判成 `failed`。

**第二次尝试（改完夹具再改代码）挖到了真正的原因，但没走到绿：**

| 发现 | 说明 |
|---|---|
| **① 页面脚本是 `toString()` 后 eval 的** | `pageScript.toString()`（第 1022 行）。**模块级常量与函数在浏览器作用域里不存在** —— 我引用了 `SECTION_RELATED_ASIN_LIMIT`（模块级）、`asinFromHref`（733 行）、`clean`（2114 行），三个全在 1227 行之前/之后，**都不在页面脚本内**。这会让整节直接 `failed`，而报错只在 `readSections` 的 catch 里存成一行 message，看起来像"页面读不出来"。 |
| ② 换成字面量 + 内联正则后 | 状态从 `failed` 变成 `missing` —— 不再抛错，但取不到 ASIN |
| ③ 加临时探针打印 | `cards=0  raw=0` —— `document.querySelectorAll('[data-cel-widget^="CardInstance"]')` 在夹具里返回 0，**即使我已在夹具的 `lists` 里加了那个键**。说明页面脚本拿到的 `document` 与被改的那个夹具对象不是同一个（或夹具里还有第二份 `lists`）。这一层我没查完。 |

**已全部 `git checkout` 撤回，全量回到 2167/0；认领以 `abandoned` 释放，留痕。**

> **下一轮的正确入口（省掉我今天踩的四个坑）：**
> 1. **先确认页面脚本作用域规则**：写任何 `readXxx` 前，只用 1227 行**之后**定义的辅助函数
>    （`tidy` / `elementText` / `queryAll` / `clipText`），**绝不引用模块级常量**；上限一律走 `ctx.limits` 或字面量。
> 2. **先摸清夹具的 `document` 到底是哪一个**（`raw=0` 那一步），再动读取器。
> 3. 夹具里加卡片时，用 `el({ children: { 'a[href*="/dp/"]': [...], 'h2, ...': [...] } })`
>    —— 子节点按**精确选择器键**查表，与真实 DOM 不同。
> 4. 断言要同时钉两件事：非广告卡进 `related_asins`、**广告卡不进**。

> 结论：**A1 仍是当前唯一"不花钱就能做通"的竞品来源**，但它卡在两个作用域陷阱上
> （页面脚本的模块级不可见 + 夹具的假 document），不是业务逻辑问题。



### 缺口 B：产品线自动归类

产品线已有 signals（`bench-cushion` 内置 9 词），分类函数已经存在（关键词那边在用）。
**建议：采集入库后自动跑一次分类，`dryRun` 先报"会把哪些 ASIN 移到哪条线"，人确认后写。**
理由：分类会改变下游所有报告的口径，自动写而不报影响面，等于悄悄改历史。

### 缺口 C：两套关键词库

- `keyword`（模块 08）：测排名、分层、所有权、位置计划
- `kw_master`（模块 07）：SOP 词表导出（标题/五点/后台/广告/否定词）

**建议：明确主从，而不是合并。**
优化用的是**模块 08 的词**（因为它有排名与分层），导出 SOP 时才需要 `kw_master`。
所以补一条**单向桥**：`keyword` → `kw_master` 的 fact 层（`source=browser-local`，
搜索量留 null 并标"无来源"），跑一次 `kw_merge`。
**不要反向**（把 ABA 的量倒灌进 keyword，会让"没测过"变成"测过量是 0"）。

### 缺口 D：政策/算法知识

**这是最需要克制的部分。**

现状：`amzn_policy_import` / `amzn_policy_link` 有政策库；规则集 2026.4 有 72 条；
站点字符上限是**已核验的市场事实**（`marketplaces.js`，带核验日期）。

外部公开信息（**待核验信号，不可直接当规则**）：
- 2026 年前后多篇中文服务商文章称「标题判定从关键词抓取转向 AI 助手可理解性」，
  建议「主标题 30–50 字符 + 亮点段 ≤150」，总量 80–120；
- 有服务商博客称 Rufus 在 2026 年 5 月退役、由 Alexa for Shopping 承接（**未证实**）；
- 这些说法互相之间并不一致，且没有一条给得出 Amazon 官方出处。

**建议的进路（三条，缺一不可）：**

1. **政策只能从政策库进**：来源 URL + 生效日期 + 严重度提示，页面可查。
   `amzn_policy_import` 已支持，缺的是"优化证据包引用 policy 这一类"。
2. **算法偏好不好写成规则**：把它写成**策略卡里的一条假设**（"本轮假设 AI 助手偏好
   语义通顺的两段式标题"），并在报告里标为「假设，未核验」。这样它可被证伪，
   而不是变成一个永远正确却没人知道来源的规则。
3. **A/B 用观测代替争论**：`F14-08 实验设计` 已经能做（假设/基线/成功指标/观测窗口）。
   与其争论"80–120 字符更好"，不如对半开跑 14 天。

> 一句话：**规则管"合法"，假设管"更好"，实验管"哪个真的好"。** 三者不能混。

## 4. 输出格式（你要求的那个）

现在的报告有 `rationale`，但缺两块。建议每个字段一条**三联账**：

```json
{
  "field": "title",
  "original": "Custom Size Bench Cushion, 75D High Density Foam Filling",
  "optimized": "ROFIEJOX Custom Bench Cushion, 75D High-Density Foam, ...",
  "why": {
    "rules": ["title.length.max", "title.anchor.first80", "title.brand.prefix"],
    "evidence": ["B0GV55Q4JG/attributes.fill_material=Foam", "kw: bench cushion (T3)"],
    "assumptions": ["AI 助手偏好语义通顺（未核验）"]
  },
  "expected": {
    "primary": "前 80 字符出现核心词 + 品牌（移动端截断前可读）",
    "metric": "自然搜索曝光 / CTR",
    "direction": "up",
    "howMeasured": "发布后 14 天，与基线 14 天比（F14-08）"
  },
  "keywords": [
    { "word": "bench cushion", "placement": "前 40 字符", "tier": "T3" },
    { "word": "custom bench cushion", "placement": "第 2 段", "tier": "T4" }
  ],
  "confidence": "high",
  "needsHuman": ["尺寸表述需与后台属性一致"]
}
```

**为什么「预期」必须写死指标和方向**：写"提升转化"是空话；
写"14 天内自然曝光升、CTR 不降"才能被观测模块判真假。

## 5. 需要你拍板的三个决定

1. **竞品发现走哪几路？** 我建议默认 A3（关键词重叠），A1/A2 作补充。
2. **品牌故事 / A+ / 主副图要不要写回？**
   现状：只出草案。Amazon 侧图片与 A+ 没有稳定 API 写回路径，
   建议保持"草案 + 人工上传"，并在报告里给可直接复制的文案与图片规格清单。
3. **外部算法说法怎么用？** 我建议一律按「假设」处理（可证伪、可实验），
   绝不写进规则集。你若要求写进规则，我需要一条可引用的官方出处。

## 6. 落地顺序（建议）

| 批 | 内容 | 为什么排这里 |
|---|---|---|
| P1 | 竞品自动发现（A3）→ 候选集 → 人勾选建组 | 现在完全靠人，是流程里最硬的人工断点 |
| P2 | 采集后产品线自动归类（dryRun 报影响面） | 影响下游所有报告口径，必须先看影响面 |
| P3 | `keyword → kw_master` 单向桥 | 打通"测词 → 导 SOP 词表" |
| P4 | 政策库接入优化证据包（第 11 类证据） | 让"最新政策"有出处、有生效日 |
| P5 | 报告加「预期」与「逐字段埋词账」 | 你的数据格式要求 |
| P6 | Optimize Job 状态机把 11 个工具串起来 | 最后做，因为前五项决定它的形状 |

## 7. 这份方案证明不了什么

- 外部"2026 算法变化"的说法**没有一条来自 Amazon 官方**，全部标为待核验信号；
- 竞品自动发现的三路可信度是我的经验判断，**没有在本仓实测过命中率**；
- 字符数上限来自 `marketplaces.js` 的已核验事实，但**规则集与站点事实是两套**，
  改上限需要走站点核验流程，不能直接改常量。
