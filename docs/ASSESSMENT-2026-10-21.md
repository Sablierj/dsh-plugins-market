## 一、外部经验：两条主线

### 1.1 亚马逊侧：2026-05 之后，竞争点从「关键词」变成「证据一致性」

2026-05-13，亚马逊下线了独立的 Rufus，把 AI 助手合并进**主搜索框**（Alexa for Shopping）。
多家来源对卖家的含义指向同一件事：

| 来源 | 关键结论 |
|---|---|
| [AMZ123](https://www.amz123.com/t/9ipZSiZX) | 买家可以越说越少，**卖家不能越写越少** —— 系统能不能"秒懂"买家靠上下文，而你的产品能不能进推荐池，取决于平台能不能**稳定理解你的产品是什么** |
| [雨果网](https://www.cifnews.com/article/186523) | 决定可见性的核心因素已变为 **Listing 的结构化信息质量** —— 能否被当作"产品知识文档"做语义理解 |
| [Seller Sprite](https://www.sellersprite.com/en/blog/amazon-alexa-for-shopping-listing-optimization-2026) | 同一方向：面向 AI 发现重写 listing |

**"证据一致性"是这套说法的核心**：

- 标题、五点、A+、图片、视频、评论、问答、广告点击与购买行为，**都是证据**；
- 证据指向同一方向 → 系统对"你是谁"越来越确定；
- 证据互相打架 → 系统迷糊，主身份被稀释。

原文举的例子很具体：一款水上运动防水包，如果页面里同时写
`laptop backpack` / `school backpack` / `travel backpack` / `beach bag`，
看起来覆盖面很广，实际上**把主身份冲淡了**。

关键词的位置也变了：它不再是"可以被单独匹配的词"，而要放进
**具体人群 + 具体场景 + 具体购买任务**里一起被理解。
所以五点的写法从「High Quality Material / Large Capacity」这种形容词，
转向「Built for Wet Water-Sport Days」这种**任务 + 结构证据**。

> 文中同时提醒：涉及测试才能证明的功能说法要谨慎，实事求是。这条与本仓的铁律一致。

### 1.2 Agent 侧：工具不是 API 包装，是给非确定性系统的契约

Anthropic 的 [Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)
把工具设计的要点说得比我们现在的做法更狠：

| 原则 | 原话大意 | 对我们的含义 |
|---|---|---|
| 少而深 | "More tools don't always lead to better outcomes"；**不要只是包装 API 端点** | 138 个工具里有多少是"API 包装"？ |
| 合并多步 | 与其 `list_users`+`list_events`+`create_event`，不如一个 `schedule_event` | 我们的 optimize 有 11 个工具走一条链 |
| 命名空间 | 按服务/资源分组，帮 agent 选对工具 | 我们只有 `amzn_` 前缀，关键词相关 28 个挤在一起 |
| 上下文效率 | 分页/过滤/截断，默认值要合理 | 部分工具一次性返回大表 |
| 描述即 prompt | 像给新同事讲一样写清术语与关系 | 我们的描述普遍很细（见下），这点是优点 |
| 评测驱动 | 建评测任务、量、再改 | **我们完全没有这一层** |

## 三、逐个页签评估

判定分四档：**保留**（做得对，继续）/ **加厚**（方向对但太薄）/ **收窄**（功能过多或重复）/
**新增**（现在的空白）。

### 工作空间与基础

| 页签 | 它该干什么 | 现状 | 对外部经验的差距 | 判定 |
|---|---|---|---|---|
| **首页** | 进去就知道：有什么数据、多新、规则哪版、该做什么 | 六张健康卡 + 今天该做什么 | 五张卡分母为 1；没有"插件提供什么"的全景；没有"规则/政策是哪一版" | **加厚** |

## 四、六个跨模块的结构性问题

### ① 工具面太大，而且没有评测兜底

138 个工具、5.8 万字符说明。按 Anthropic 的经验，**工具越多，agent 越容易选错**，
而"选对工具"这件事我们**从来没有量过**：

- 108 个套件测的是**代码行为**（这个函数返回什么）；
- 没有一个套件测**"给 agent 一句话，它能不能用这些工具把事做完"**。

这是最贵的空白：我们优化了 138 个零件的正确性，却没测过这台机器能不能开。

### ② 缺「证据一致性」——正好是 Alexa 时代的核心能力

外部经验说得很清楚：胜负在于**所有材料是否指向同一个产品身份**。
我们现在有：

- 逐字段校验（标题超长、禁用词）；
- 关键词覆盖矩阵；
- 属性覆盖 17/43。

**没有**：跨材料一致性检查。标题说"水上运动"、五点说"通勤"、A+ 说"学生"——
系统一句都不会报。这恰恰是 2026 年最该有的一条检查。

### ③ 政策是文字，规则是代码，两者只在"挂没挂上"这一层连接

已修的挂空检查只回答"这条政策引用的规则在不在生效集"。
回答不了"政策和规则给的数值不一样"。要回答，政策得先有结构化约束
（字段 / 上限 / 单位），否则只能解析自然语言 —— 那不该猜。

### ④ 两套词库仍然并存

`keyword`（模块 08：排名/分层/生命周期）与 `kw_master`（模块 07：SOP CSV）。
桥已经在 `recomputeMaster` 里，但对使用者来说仍是"两个地方看词"。

### ⑤ 数据入口太窄

四个模块（竞品、关键词、政策、优化）功能齐全但没有输入。
商业数据源（卖家精灵/西柚/赛狐）全是"未接入"，而它们是竞品词与搜索量的**唯一**来源。

### ⑥ 「管理入口」的定位还没有落到界面上

需求方的定位是：**插件提供规则、标准引导和数据；会话负责灵活执行；工作台是回头看的控制室。**

现在的工作台更像"功能罗列"：15 个页签平铺，没有回答三个最该回答的问题——
**我有什么数据 / 它新不新 / 现在该按哪版规则办事。**

（右侧栏已在今天拆掉，那一块腾出来的位置正是给这三个问题留的。）

## 五、建议：下一轮做什么

### P0（先做，因为不做后面都是空转）

1. **把数据灌进来**：至少 5–10 个 ASIN、竞品组、一批政策。
   没有原料，任何优化能力都无法验证。
2. **建 agent 级评测**：10–20 个真实任务（"把这个 ASIN 的标题改到 200 字符以内并保住主身份"），
   量成功率、工具调用数、token。这是唯一能判断"138 个工具是不是太多"的方法。

### P1（结构）

3. **加「证据一致性」检查**（新增能力，不是新页签）：
   主身份词 vs 五点场景 vs 属性 vs 图片 alt，冲突要报出来。
4. **关键词工具收窄**：28 个 → 目标 12 个以内，按"调研 / 归属 / 计划 / 导出"四组命名空间。
5. **政策结构化**：`constraints_json`（字段/上限/单位），让政策可被机器比较。

### P2（体验）

6. **首页改成控制室**：数据全景 + 规则/政策版本 + 异常，而不是六张分母为 1 的卡。
7. **两套词库合一**（或明确分工并在界面上写清）。

## 六、界面与设计（本轮实测，不是凭空评）

> 方法：把工作台在 1366×768 的窗口里真的打开、逐页看、并把 CSS 的设计令牌数了一遍。
> 以下每条都有出处（截图 / 代码行 / 实测数字）。

### 7.1 实测到的六个问题

| # | 问题 | 证据 |
|---|---|---|
| 1 | **`undefined` 直接显示在界面上（9 处）** | 关键词总库的「生命周期九态」条：`candidate undefined　active undefined　assigned undefined`…… 九个状态各一个 |
| 2 | **结论与数字自相矛盾** | 首页「字段完整率　**正常**　0/1 个 ASIN 的 listing 有标题/五点/描述」—— 0/1 不可能是正常 |
| 3 | **「趋势：不知道」在六张卡上重复六次** | 首页每张卡都这一行。诚实，但**六张都这么写，等于这行没有信息**；真正该说趋势的地方反而被稀释 |
| 4 | **没有字号层级** | `page.js` 里 105 处 `font-size`：**11px×30 + 12px×70 = 100 处**，13/14/15/22px 各 1 处。标题靠加粗和灰色区分 |
| 5 | **控制台里塞着说明书** | 关键词页正文有两段 100+ 字的规范解释（「主持人 = 谁唯一生效主条…」「计划是分配决定…」），行宽约 1150px，中文一行 100+ 字 |
| 6 | **空列不说明为什么空** | 关键词表「搜索量」整列为空（没有第三方数据），表内没有任何提示 —— 读者分不清「没数据」和「没查」 |

### 7.2 信息架构：17 个导航项平铺，按"模块"而不是按"任务"组织

现在的左栏（6 组、17 项，全部展开、无折叠）：

```
工作空间与基础   工作台首页 / 站点与采集配置 / 数据源管理 / 产品线管理 / 数据资产与质量
采集与数据      采集器 3 / ASIN 数据管理 1 / 竞品数据分析
关键词          关键词总库 / 关键词调研 16 / 关键词管道
规则与政策      规则获取 / 最新政策
优化与报告      优化队列 0 / 报告专区 / 优化提示词专区
执行与编排      Agent 编排
```

问题在于**分组是按代码模块分的，不是按使用者的任务分的**：

- 「数据源管理」「产品线管理」「站点与采集配置」三件都是**设置**，却占着第一组最显眼的位置；
- 「数据资产与质量」是**巡检**，和采集混在一组；
- 一个运营一天的顺序其实是：看板 → 采集/补数 → 干活（关键词/优化）→ 复盘（报告），
  现在的顺序把这个链路切成了五段。

### 7.3 建议的结构（按任务，不按模块）

```
┌ 顶栏：站点 · 作用域 · 数据新鲜度 · 全局搜索 ─────────────────────────┐
├ 左栏（4 组，可折叠）────────────┬ 主区 ────────────────────────────┤
│ 概览   今天该做什么              │  ① 状态条：有多少数据 / 多新 / 有什么问题 │
│ 数据   ASIN · 关键词 · 竞品 · 采集 │  ② 主体：表格或表单                  │
│ 规则   规则 · 政策 · 提示词        │  ③ 说明：折叠（现在那些大段文字收进来）   │
│ 优化   队列 · 报告                │                                     │
│ 设置   站点 · 数据源 · 产品线 · Agent │                                     │
└─────────────────────────────────┴─────────────────────────────────────┘
```

**每一页统一三段式**（状态条 / 主体 / 折叠说明）。这一条同时解决 7.1 的 #5 和 #6：
说明不再占据正文，空列的原因写在状态条里。

### 7.4 视觉：先建立层级，再谈好看

| 项目 | 现在 | 建议 |
|---|---|---|
| 字号 | 11/12px 为主，无层级 | 页标题 18 / 区块 14 semibold / 正文 13 / 辅助 12 |
| 行宽 | 正文可到 1150px | 说明类文字限宽 68–72 字符（中文约 32–36 字） |
| 圆角 | 5/6/7/8/9/999 六种混用 | 统一 8px（胶囊仍用 999px） |
| 颜色 | 已有 light/dark 两套变量，语义色 ok/warn/stop/accent 齐全 | 保留；补一条：**语义色只用于状态，不用于装饰** |
| 数字 | 无等宽 | 所有计数/比例用等宽数字（表格已部分这么做） |

### 7.5 状态与反馈：三种"空"必须在界面上分开

系统内部已经区分得很好（frozen / absent / not_modelled），但界面只显示空白。
这是最值得抄自己作业的一处 —— **把内部的诚实搬到界面上**：

```
这一列没有来源        ← 本仓没有这个数据源
这一列读过了，是 0 条  ← 有来源，结果是 0
这一行还没测过        ← 有来源，但没对这条测
```

### 7.6 这一节的边界

- 只看了 1366×768 与最大化两个窗口；**没有**测超宽屏、深色模式实机、键盘全流程。
- 没有做可用性测试（没有真实用户操作录像），所以"难用"的判断来自结构阅读 + 实测截图。
- 上面所有"建议"都是**结构性**的，不涉及具体像素级视觉稿。

## 七、这份评估证明不了什么

- 它**没有**验证 138 个工具在真实会话里的表现 —— 那需要 P0-2 的评测。
- 外部经验来自公开文章，**不是亚马逊官方文档**；"证据一致性"是行业解释，
  亚马逊从未公布 Alexa for Shopping 的排序权重。
- 数据量太小（1 个 ASIN），所有"现状正常"的结论都只在这个样本上成立。
- 本评估没有改动任何代码。
