**所以「补齐」的诚实写法不是造九个字段，而是三件事**：
1. 把**已经写着但做不到**的话改对（`roles.js:22-23` 的过度承诺）；
2. 把**现在真的能做**的出口接上（blocked 的两个可执行动作）；
3. 把**没有数据来源**的要素**如实登记成一条记录**（对齐 `metrics.js:102-106` 已有的范式），
   而不是给它们编一个像数据的替身。

> **本仓铁律**：给缺失造一个像数据的替身，比留一个洞更危险。

## §1 缺陷形状（本批要修的就是这个形状）

三个独立形状，都是本仓反复出现的：

**(a) 注释比代码强** —— `roles.js:22-23` 逐字写着：

> 所以 `steps` 是**契约**：Agent 按它逐步回报，**插件按它校验顺序与工具权限**。

实测：`recordStep`（`store/agent.js:224-259`）**只按 `seq` upsert**，
不校验 `step` 是否在 `role.steps` 里、不校验顺序、不触发下一步。
全仓没有任何代码因 `steps` 而拒绝任何东西。

同一个文件头对 `tools`/`forbidden` 是**诚实的**（明写「是声明的范围，不是强制边界」），
唯独 `steps` 这句「插件按它校验顺序与工具权限」**没有被自己澄清** —— 这是过度承诺。

**(b) 零读者导出** —— `roles.js:202`：

```js
export const AVAILABLE_ROLE_IDS = AGENT_ROLES.filter(role => role.available === true).map(role => role.id)
```

`grep -rn AVAILABLE_ROLE_IDS src/ tests/ index.js` → **只命中定义行本身**。
页面用 `data.roles.filter(role => role.available)`（`page.js:3994/4036`）自算，
路由用 `roleView`（`routes.js:3339`）。**零读者。**

**(c) 「缺失」被折叠成「空」** —— `store/agent.js:460-462`：

```js
export function listArtifacts(store, runId) {
  return getRun(store, runId)?.artifacts ?? []
}
```

零生产调用（全仓 4 处提及 = 定义 + `wired-source.mjs` 登记 + 一处注释引用 + 文档）。
它返回的形状与 `getRun(...).artifacts` **逐字段完全相同**，所以是退化副本。
但它多带一个缺陷：`?.` + `?? []` 把两种不同的事实折叠成同一个 `[]`：

- 运行**不存在** → `getRun` 返回 `null` → `?.` 短路 → `[]`
- 运行**存在但没产物** → `.artifacts` 本就是 `[]` → `[]`

而 `getRun` 自己的契约是**明确区分两者**的（`store/agent.js:75` 注释
「`null` when there is no such run」）。**`listArtifacts` 把这个区分抹掉了。**

> 这与 F11-07 `listEvalCases` 是同一形状 —— 那次是 `?? []` 把
> 「没有这一套」与「这一套是空的」折叠。判据：
> **「没有这一个」→ `null`；「这一个存在但是空的」→ `[]`；两者必须分开。**

### §7.2 ⚠️ 对抗验收查出的两处缺陷（本批最重要的一段）

独立验收员打穿了两处，**两处都不在任何断言里** —— 又一次印证「测试全绿 ≠ 没缺陷」。

**(1) 断言永远绿不了（BROKEN）** —— `tests/m12-agent.mjs:458`：

```js
await check('the two zero-reader exports are gone...', async () => {   // ← 同步 check + async 回调
```

`run.mjs:339-341` 在回调返回 Promise 时**主动抛错**：

```js
const result = fn()
if (result instanceof Promise) throw new Error('use checkAsync for async assertions')
```

所以这条断言**在任何实现下都不可能通过**（包括正确实现）。实现者报的
「m12 13 passed / 0 failed」不可复现，真实读数是 **12 passed / 1 failed**。

> **这条的形状值得单列**：一个**永远红**的断言和一个**永远绿**的断言一样是缺陷 ——
> 它会训练所有人「这条红是正常的」。而它伪装成了「本批新增的负向断言」。

**修法**：`check` → `checkAsync`（`checkAsync` 早在 `:126` 已解构）。
修后 **13 passed / 0 failed**。

**(2) 文案比事实强（OVERSTATED）** —— `src/domain/agent/gap.js:67`：

原文「**全仓** `fallback` 只命中 `src/store/agent.js:66` 的 `JSON.parse` 第二参数」。
实测 `fallback` 在**全仓**约 200 处命中；该说法只在**模块 12 范围内**成立。
语义结论站得住（模块 12 内唯一命中确为 `JSON.parse` 兜底，语义无关），
所以**改的是措辞的适用范围，不是结论** → 「模块 12 内 grep `fallback` 只命中…」。

> 判据：**「在某范围内成立」被写成「全仓成立」也是文案比事实强的一种**，
> 与「写了白名单却没有拦截」同族，只是更隐蔽（因为它**在某个范围内是真的**）。

### §7.5 已知边界（交付后补正）

- **否定性 grep 不是证明，是证据**。「`permission_request` 零命中」这类结论
  只能证明**没有叫这个名字的东西**，不能证明「没有等价物换了个名字」。
  已用 `权限申请`/`approval`/`gate` 多词交叉查，仍为零，但**这仍不是穷尽证明**。
  所以本批的做法是**不编按钮**（少做）而不是**断言不存在**（多承诺）。
- **块 C 登记的是「缺哪份记录」，不是「补法」**。九项仍然缺九项；
  本批的差别只在于它们**从文档走进了可查询的结构化记录**，能与代码对账。
- `listArtifacts` 删除**可能**影响某人将来的便利写法。裁决理由：它是
  `getRun(...).artifacts` 的一行语法糖**且带缺陷**（把「运行不存在」折叠成「没有产物」）；
  要便利直接用 `getRun`。

### §7.6 全量套件：前两次失败，第三次拿到真读数

> **结论：`1454 passed / 0 failed / EXIT=0`**（日志 `/tmp/b125b-full.log`，2020 行）。
> 跑前跑后 `key.js` / `optimize.js` 的 md5 逐字一致，无 `.bak` 残留，工作树干净。
>
> 两条新增断言在**真实宿主**下确认通过（不是只在独立驱动里）：
> · `:967` `ok the two zero-reader exports are gone, and are not replaced — A2 A3`
> · `:1006` `ok ⑨ the gap register renders from the payload, and an absent payload draws no undefined`
>
> 工具数在真实宿主日志里也是 **112**（三种 `amzn_prompt_eval_*` 均在注册表内）。

**前两次为什么没成（如实记，因为这是可复用的坑）**：

1. 第一次：后台启动后日志停在 **160 行**且无 `EXIT=` 标记；`Get-CimInstance`
   证实进程**确实还在跑**（PID 20996），但我的轮询循环收到 **SIGTERM**，
   运行被中断。**中断的运行不能算证据。**
2. 第二次：`nohup … &` 在工具内**丢失了重定向目标**（`/tmp/full-run.log` 从未创建，
   而 PID 19080 确实在跑 `tests/run.mjs`）。**进程在跑、日志不存在** —— 这是最坏的一种，
   因为「任务在后台运行」的提示会让人以为一切正常。
3. 第三次（成功）：先 `: > /tmp/b125b-full.log` **预创建并 `ls` 确认可写**，
   再重定向。跑的过程中我的轮询仍被 SIGTERM 过两次，**但 node 进程不受影响**
   （`Get-CimInstance` 确认 PID 41744 存活），日志持续增长到 2020 行。

**判据（写给后来者）**：
- 本仓全量跑**不要用 `&` 在工具里后台启动** —— 重定向会静默丢失。
  先预创建日志文件，用 `run_in_background` 重定向。
- **日志停住 ≠ 进程死了**（输出成批缓冲）。判进程死活看 `Get-CimInstance Win32_Process`，**不看日志**。
- **`tests/run.mjs` 是个写者**：它会临时改写 `key.js`（无 `.bak`）与 `optimize.js`（有 `.bak`）。
  跑前跑后必须 `md5sum` 对账，并查 `.bak`/`.orig` 残留。
- ⚠️ **日志里出现 `0/3 passed` 不是失败** —— 那是 `check-page.mjs` 的**负向对照**
  （故意注入断开模板字面量的反引号，断言检查器能抓到它），紧接着的 `3/3 passed`
  才是干净文件的正向对照。**读全量日志时必须看上下文，不能只 grep `passed`。**
