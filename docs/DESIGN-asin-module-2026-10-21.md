## 一、那套系统的 ASIN 列表做了什么

**9 个筛选**：ASIN、搜索标题、产品线、类型（自有/竞品）、**五点数（≥5 / ＜5）**、
**描述（有/无）**、**A+（有/无）**、**健康等级 S/A/B/C**、**分组（含「未配置分组」）**。

**8 个动作**：

| 动作 | 说明 |
|---|---|
| 查询 / 刷新 | —— |
| 视图模式切换 | 卡片 / 表格（radio） |
| **批量采集 (N)** | 选中即采 |
| **批量诊断 (N)** | 选中即诊 |
| **分组配置** | 主 ASIN + 变体列表 + 采集补充 + 检查 ASIN 状态 |
| **竞品映射** | 已映射 / 推荐两个 tab，支持「批量添加」智能推荐 |
| 产品线入口 | 跳产品线管理页 |
| **打包下载 (N)** | 选中即打包 |

**表格列**：选择框 / ASIN / 品牌 / 分组 / **诊断徽章**（有结果就显示） / **主图缩略图** /
标题 / 价格 / 评分 / **产品线（行内下拉直接改）** / 采集状态 / 操作（详情·采集·诊断）。

**数据模型**（`models/asin.py`，12 字段）：asin、brand、title、price、rating、review_count、
bsr_rank、bsr_category、**raw_data(JSONB)**、**is_competitor**、**group_asin**、product_line、
collected_at、updated_at。API 另有 `/stats`（统计）、`/brands`（品牌下拉）、
`/{asin}/history`（文件系统里的最多 3 个历史版本）、`batch-update`、`group-update`。

## 二、我们强在哪、弱在哪

| | 他们 | 我们 |
|---|---|---|
| 详情 | 表单 + 属性表 + raw JSON | **9 个 tab**：概览 / 字段（含来源·新鲜度·人工确认）/ 13 个采集区块 / 变体（含矛盾检测）/ 关键词与排名 / 评论 / 竞品对比 / 优化历史 / 溯源审计 |
| 来源与时间 | 一个 `collected_at` | **字段级 provenance + 快照历史 + diff** |
| 删除 | 直接删 | **归档优先，删除需确认且查引用** |
| 列表 | **运营看板**：9 个筛选 + 8 个动作 + 行内编辑 + 统计 | 数据表：搜索/站点/产品线/品牌 + 列选择器 + 保存视图 |
| 变体 | `group_asin` 一个字段 | `asin_variant` 表 + 矛盾检测，但**没有"一次配一组"的入口** |
| 竞品 | `is_competitor` 布尔 + 竞品映射对话框 | `competitor_set` 独立页，**ASIN 页没有入口** |

**结论：详情我们更强，列表他们更强。** 这一批补列表。

## 三、本批做了什么

### 3.1 ASIN 组合概览（页面顶部一排 chip）

```
共 1 条 · 归档 0 · 未归属产品线 1 · S 0 · A 0 · B 0 · C 1 · 缺标题 0 · 五点不足 0 · 缺描述 0 · 无 A+ 1
```

数字为 0 的也照画 —— 少一个 chip 会让人以为"没查"。

### 3.2 内容完整度分级 S/A/B/C

| 等级 | 判据 |
|---|---|
| **S** | 标题 + 五点 ≥5 + 描述 + A+ + 属性 ≥10 |
| **A** | 标题 + 五点 ≥5 + 描述（缺 A+ 或属性少） |
| **B** | 有标题，但五点 <5 或没有描述；五点 ≥3 |
| **C** | 没有标题，或五点 <3 |

**它不叫"健康度"**：`amzn_asin_health` 才是健康度（43 属性覆盖 + 九道门 + 时效 + 冲突），
那是**一条一算**的重查询，不能对列表每行都跑。这里的 S/A/B/C **只说明内容齐不齐**。

### 3.3 一个语义决定：标题取两个来源

`listing.title`（采到的文案）或 `asin.title`（主数据）**任一有就算有**。
只采到主数据、还没采到文案时，报"缺标题"会误导 —— 那是"文案还没采"，
由 `noListing` 单独计数。

## 四、还没做（按价值排序）

1. **按内容缺口筛选**（缺口最大的那个）—— 现在概览只能"看"，不能"点进去"。
   要做需要在 `queryAsins` 上加 `listing` 的 JOIN 条件（服务端筛选，不能拿当前页糊弄）。
2. **行内改产品线** —— 他们下拉一改就保存；我们只能走 `amzn_asin_upsert`。
3. **分组（变体族）一次配置** —— 我们 `amzn_asin_variant_upsert` 一次一条。
4. **竞品映射入口** —— 把 `competitor_set` 的选取搬到 ASIN 页。
5. **批量采集** —— 选中 N 条直接提交采集任务（我们已有 `amzn_collect_run`，缺页面入口）。
6. **主图缩略图列 / 诊断徽章列**。

## 五、这份文档证明不了什么

- 没有跑过那套系统的实际页面（只读了前端源码与路由），所以"他们好用"是**读代码得出的**，
  不是用过之后的评价。
- 我们的 S/A/B/C 门槛（五点 ≥5、属性 ≥10）是**设计值**，没有用真实数据校准过 ——
  现在库里只有 1 个 ASIN，校准不了。
- 概览是**一次全表查询 + Node 侧聚合**，30 万 ASIN 时可能要换成分组 SQL。
  当前量级（1 条）看不出这个边界。
