# SIF 数据台 · 插件设计方案（v0.1）

> 目标：把 SIF MCP 的 32 个工具，变成**一个每天自动落库、按 ASIN / 关键词 / 时间三轴可查、能给结论的本地运营台**。
> 不是「把 MCP 工具再包一层」，而是「MCP 只负责取数，结论从本地库里算」。

## 1. 为什么是独立插件，而不是塞进 amazon-ops

| 方案 | 代价 | 结论 |
|---|---|---|
| A. 改 amazon-ops（加表 + 加源 + 加页） | 它已有 178KB schema、300KB 路由、68MB 库，且带 5 个 P0 未清；每加一张表都要动迁移链和五大页签 | ✗ 风险与大改成本不匹配 |
| B. **独立插件 sif-ops，自有 SQLite** | 与 amazon-ops 无耦合；ASIN/关键词用字符串对齐，需要时只读 attach `amazon-ops.db` 拿主档 | ✓ **推荐** |

两者的分工写死，避免做成两套互相矛盾的主数据：

- **amazon-ops**：ASIN 主档、Listing 文本、采集任务、优化草案、报告库（「我对这个 ASIN 做了什么」）
- **sif-ops**：SIF 口径的**流量 / 广告 / 关键词 / 市场**四域时序与诊断（「市场和平台怎么看这个 ASIN」）
- 桥接：sif-ops **只读** attach `amazon-ops/data/amazon-ops.db` 的 `asin` 表，用于补 title/brand/上架日；不写它的库。

## 2. 插件形态

```
sif-ops/
  package.json            # name: dsh-plugin-sif-ops, dsh.bundle.patch + dsh.client.platform=web
  cordis.patch.yml        # 一行 host：plugin: workbench（绝对路径，与 amazon-ops 同法）
  index.js                # host 半：注册 sif_* 工具 + web 路由 + 定时同步
  lib/client.js           # 浏览器半：侧边栏入口 + iframe 面板（照 amazon-ops 的成熟写法）
  src/mcp.js              # MCP 客户端（streamable-http + Bearer + 会话复用 + 重连）
  src/store/db.js         # node:sqlite（Node 24 自带，零依赖）
  src/store/schema.js     # 迁移链 MIGRATIONS + SCHEMA_VERSION
  src/store/queries.js    # 读写 + 视图
  src/sync/*.js           # 每个工具一个 importer（normaliser），把 JSON 摊平成行
  src/analysis/*.js       # 本地规则：缺口/依赖/动量/季节/集中悖论
  src/web/{page.js,routes.js}  # /custom/sif-ops 自包含页面 + JSON API
  data/sif.db             # 本地库（WAL）
  data/config.json        # 连接配置（密钥，0600）
```

零第三方依赖：`node:sqlite` + 原生 `fetch` + DSH 插件 API（与 amazon-ops / pdd-workbench 同一套已验证范式）。

## 3. 侧边栏入口

复用已验证的两条 slot 契约（`memory-bridge` / `amazon-ops` 都在用）：

```js
ctx.slots.inject('main', () => ctx.slots.register({ name: 'main', key: 'sif-ops' }, Panel))
ctx.slots.inject('sidebar.panellist', () => ctx.slots.register(
  { name: 'sidebar.panellist', id: 'sif-ops', order: 11, label: 'SIF 数据台' }, Glyph))
```

- 图标：自制 SVG（图谱/关键词柱状），只吃 `currentColor`，随主题明暗切换。
- `order: 11` 正好排在「Amazon 运营工作台(10)」下面——两个台子挨着，符合它们的分工。
- 面板 = `iframe src="/custom/sif-ops"`，与 amazon-ops 同法，页面自包含、无外链。

## 4. 页面结构（5 个页签）

| 页签 | 解决什么 | 主要交互 |
|---|---|---|
| **连接** | 配 mcp.sif.com、验密钥、看余额 | Endpoint（默认 `https://mcp.sif.com/mcp`）/ 鉴权方式（Bearer · OAuth 预留）/ 密钥（存本机，回显仅后 4 位）/「测试连接」→ initialize + tools/list + `query_quota`（**0 点**）/「保存」/「重建会话」 |
| **对象** | 我盯哪些 ASIN 和关键词 | ASIN 清单（增删、分组、备注「我的/竞品」）、关键词清单（词根 + 目标词）、每个对象显示「最后同步时间 / 数据截止日」 |
| **同步** | 花钱的入口，必须可预算 | 三档节拍（L1 日报 / L2 周报 / L3 按需）、**调用前显示「本次预计扣 X 点，余额 Y」**、逐对象勾选、跑完显示每工具扣点与入库行数 |
| **看板** | 一屏看清该做什么 | ASIN 卡：流量总分 7/28 日趋势、自然 vs 广告占比、头词自然位、缺口位差、ABA 动量、上周广告结构变化；按「缺口严重度 × 流量占比」排序 |
| **洞察** | 结论与待办 | 规则引擎产出的条目（缺口/广告依赖/结构性下滑/集中悖论/旺季窗口），每条带证据（哪个词、哪一周、差几位），可一键生成 markdown 报告 |

配置页的三条硬规则：

1. **密钥不进 cordis.patch.yml**（那份文件会进备份、进 git）。写入 `data/config.json`，权限 0600，页面只回显 `…wv3k`。
2. **测试连接只用 0 点工具**：`initialize` + `tools/list` + `query_quota`。绝不用一次业务调用当连通性测试。
3. **连接失败分三种人话**：401=密钥错/过期；`-32601`=客户端 Accept 头不对（这是 SDK 的事，提示升级）；超时=网络/代理。不要笼统说「连接失败」。

## 5. 模型工具面（Agent 用，不是给人点的）

| 工具 | 作用 | 点数 |
|---|---|---|
| `sif_status` | 连接/配额/最近同步/库内数据覆盖区间 | 0 |
| `sif_sync` | 按对象 + 档位拉数入库；`dryRun` 先报预算 | 按档位 |
| `sif_query_traffic` | 本地读：ASIN 流量序列（周/日，含渠道拆解） | 0 |
| `sif_query_keywords` | 本地读：ASIN×关键词（份额/排名/缺口/动量） | 0 |
| `sif_query_aba` | 本地读：词的 ABA 周序列 + 需求诊断 | 0 |
| `sif_query_ads` | 本地读：campaign/ad group/词 三层贡献 | 0 |
| `sif_insights` | 规则引擎结论（可过滤 ASIN/严重度） | 0 |
| `sif_report` | 生成 markdown/HTML 报告并入库 | 0 |

**设计原则：模型只在「缺数据」时调 `sif_sync` 花钱，分析一律读本地。** 这样同一次分析重跑十遍也不扣点。

## 6. 同步编排（谁在什么时候调什么）

- **L1 日报**（每 ASIN 5 点）：`ops_get_asin_traffic_trend`(2) + `ops_get_listing_traffic_overview`(3)
- **L2 周报**（每 ASIN 6 点）：`market_get_asin_keyword_signals`(3) + `ads_get_asin_ad_structure`(2) + `ops_get_asin_sales_trend`(1)
- **L3 按需**：`market_get_keyword_history`(1/词)、`market_get_keyword_demand`(2/词)、`market_get_keyword_competition`(2/词)、`ads_get_asin_campaign_contribution_overview`(3)、`ads_get_campaign_contribution_breakdown`(3)、`market_get_asin_profile`(2/ASIN)
- **场景工具** `analyze_traffic_anomaly`(10) 不作为日常同步，只在「流量掉了、要归因」时由人显式触发。

预算闸门：一次批量同步前先算 `Σ 点数`，超过「日预算」（默认 60 点，可配）就拒绝并显示拆分。

## 7. 与已接好的 MCP 的关系

- 现有的 `mcp__sif__*` 工具**保留**：临时探数、一次性问答仍然最快。
- sif-ops 的价值在于：**同一份数据只花一次点，之后无限次分析**；页面和历史趋势不需要 Agent 在上下文里搬 300 周的数组。
- 两者共用同一把密钥、同一个配额；`sif_status` 与 `query_quota` 都要显示余额，避免「两处都在花，谁也不知道剩多少」。

## 8. 验收标准（做到这几条才算能用）

1. 侧边栏出现「SIF 数据台」，点开是 5 个页签，首屏无报错。
2. 连接页输入密钥 →「测试连接」→ 显示 serverInfo + 32 个工具 + 余额，**扣 0 点**。
3. 同步页勾 1 个 ASIN 跑 L1：显示预计 5 点、实际扣点、入库 10 周 × 7 个指标。
4. 看板显示该 ASIN 的流量曲线（自然/广告两条）、头词自然位、缺口位差。
5. `sif_query_traffic` 等读工具全部 0 点，重复调用结果一致。
6. 断网/密钥错时，页面给的是具体错误类别，不是「失败」。
