# 产品研发团队：流程与协作总纲

本文件是**唯一事实来源**：角色章程（`team-role-*` 技能）与任务书都必须与这里对齐。
角色名、阶段名、门禁名、交付物路径，一律用本文的写法，不要另起一套。

## 0. 一个前提

团队里除了你（主理人 / 项目经理）之外，其余 8 个角色**默认是「按需拉起」的**，但**两条通道不通用**：

| 通道 | 怎么派 | 事后能追加要求吗 | 能上任务板吗 |
|---|---|---|---|
| Team 成员 `spawn_teammate` | `send_message` 用**成员名**寻址 | 能（空闲成员会被唤醒） | 能 |
| 一次性子代理 `subagent` / `subagent_fork` / `workflow` | 直接派，结果自动回来 | **不能**，任务书一次写全 | 不能 |

⚠️ 四条实测限制（2026-10-13，独立复核过）：
1. 主理人的 `send_message` / `list_agents` / `interrupt_agent` 是 **Team 版**（只认 `target` = 成员名或 `lead`）；
   拿子代理的会话 id 去寻址会报 `active teammate "<id>" not found`。
2. **成员（depth 1）用不了 `subagent` / `subagent_fork`** —— 报 `subagent depth 2 exceeds maxDepth 1`
   （默认 `maxDepth=1`）。成员要扇出只能用 `workflow`。
3. `workflow` 子代理继承的是主理人的 Team 版工具、自己又不是成员：它连 `send_message` 都发不出去
   （报 `is not a member of an active Agent Team`），只能把结果当返回值交回。
4. ⚠️ **成员的启动在部分环境下不稳定**（2026-10-13 同一会话内复现 5 轮）：
   成员被分配到**不可用的模型路由**时会**启动即中断** —— `list_agents` 显示 `inactive`，
   而任务板上那个任务**仍是 `in_progress`**（它已经 claim 过了）。实测：
   分到 `cn:deepseek-v4.1-flash` 的成员**全部启动即死**；分到 `global:deepseek-v4.1-flash` 的能跑。
   **对策**：`send_message` 唤醒**会重新分配模型** —— **反复唤醒直到落到可用路由**即可（已验证有效，2/4 落对）。
   **兜底**：成员通道持续不稳定时**退回一次性 `subagent`**（同一会话里它一直可靠）。
   ⚠️ **不要因为成员 `inactive` 就以为任务失败** —— 先 `list_agents` + **看工作树**（`git status --porcelain`
   在它的 worktree 里、看最后写入时间），**盘上有没有活才是判据**。
**要能追加、要能等、要上任务板的活 → `spawn_teammate`；`subagent` 派出去的就当一次性。**

成员看不到你的对话。**任务书写不好 = 活干不好**，这是本流程里最贵的失败模式。

## 1. 八个角色

| 角色 | 技能 | 一句话职责 | 主交付物 |
|---|---|---|---|
| 产品经理 PM | `team-role-product-manager` | 把业务目标变成可验收的产品决定 | PRD、优先级、验收标准、发布说明 |
| 需求研究员 Research | `team-role-requirements-researcher` | 用证据回答「用户到底要什么、市场允许什么」 | 调研报告、需求清单、竞品/数据证据 |
| 架构师 Architect | `team-role-architect` | 定边界、定契约、定不做什么 | ADR、接口契约、数据模型、非功能要求 |
| 全栈开发 Fullstack | `team-role-fullstack-engineer` | 按契约实现，带测试和迁移 | 代码、测试、迁移脚本、变更说明 |
| UI 设计师 UI | `team-role-ui-designer` | 把交互变成可实现的视觉与组件规范 | 视觉规范、组件清单、状态图、设计 token |
| 用户体验师 UX | `team-role-ux-designer` | 把用户任务变成信息架构与交互流程 | 信息架构、用户流程、线框、可用性结论 |
| 测试工程师 QA | `team-role-qa-engineer` | 独立证明「它能用、且没坏别的」 | 测试计划、测试报告、缺陷单、发布建议 |
| 亚马逊运营 Ops | `team-role-amazon-operator` | 代表真实业务现场与平台规则 | 运营需求、合规约束、数据口径、运营周报 |

**谁不做什么**（越界的活会互相打架）：

- PM 不写技术方案，不替架构师决定实现；只决定「做什么、先做什么、什么算做完」。
- 研究员不下结论性的产品决定；只给证据、置信度和不确定性。
- 架构师不写业务代码交付，不为单个页面的视觉拍板。
- UX 不出视觉稿，UI 不改交互流程——两者互相评审，冲突交 PM 裁决。
- QA 不改被测代码（发现缺陷交回开发），不代替 PM 判断「这个缺陷能不能接受」。
- Ops 不直接改代码，只提供现场事实、规则约束与数据口径。

## 2. 流程：7 个阶段、5 道门禁

```
P0 立项 ─G0→ P1 需求发现 ─G1→ P2 体验与界面设计 ─┐
                                          ├─G2→ P4 开发实现 ─P5 测试与验收 ─G3→ P6 运营与迭代
                        P3 架构与技术方案 ─┘
```

- **P0 立项（PM）**：目标、成功指标、范围、非目标、风险。产出 PRD 的第 1 节。
- **G0 立项门禁**：目标可量化、有明确用户、有非目标、有 owner。缺一项不过。
- **P1 需求发现（Research + Ops + PM）**：用户任务、现状痛点、竞品、平台规则、数据口径。
- **G1 需求门禁（DoR，Definition of Ready）**：每条需求 = 用户故事 + 验收标准（可测）+ 优先级 + 依赖 + 非目标；
  证据标注来源与置信度；至少一条来自真实运营现场。不过就退回 P1。
- **P2 体验与界面设计（UX + UI + Ops）**：信息架构、用户流程、线框、视觉规范、组件与状态、
  空/错/加载/权限四态。UX 与 UI 互相评审，冲突由 PM 裁决。
- **P3 架构与技术方案（Architect + Fullstack）**：边界、数据模型、接口契约、迁移与回滚、
  性能/安全/可观测性、技术债取舍。每个不可逆决定写一份 ADR。
- **G2 设计门禁**：每条需求有对应流程与线框；每个接口有契约（入参/出参/错误码）；
  数据变更带迁移与回滚；非功能要求有数字。缺一不过。
- **P4 开发实现（Fullstack）**：小步提交、每步带测试、破坏性变更带迁移与开关。
  分支/提交信息写清对应的需求编号。
- **P5 测试与验收（QA + 需求提出人）**：按测试计划执行：单元 / 契约 / 端到端 / 回归 / 边界与失败路径；
  真实环境跑一遍（`pwsh`、`browser_*`、`desktop_mouse` 截图都可作为证据）。
- **G3 发布门禁**：验收标准逐条有证据；无 P0/P1 未决缺陷；有回滚方案；有可观测性（日志/指标）；
  发布说明已写。缺一不过。
- **P6 运营与迭代（Ops + PM）**：上线后回收数据，对照成功指标，开下一轮 P1。

|---|---|
| PRD / 产品决定 | `docs\requirements\PRD-<feature>.md` |
| 调研报告 / 竞品 / 数据 | `docs\requirements\RESEARCH-<topic>.md` |
| 信息架构 / 流程 / 线框 | `docs\design\UX-<feature>.md` |
| 视觉规范 / 组件 / token | `docs\design\UI-<feature>.md` |
| 架构决定 | `docs\architecture\ADR-<四位序号>-<slug>.md` |
| 接口契约 | `docs\architecture\API-<feature>.md` |
| 测试计划 | `docs\qa\TESTPLAN-<feature>.md` |

## 4. 任务书模板（派活时照抄填满）

```md
## 任务 <编号>：<一句话目标>
- 角色：<八个角色之一>
- 阶段/门禁：P?/G?
- 背景与环境事实：<这台机器上确切的事实：仓库路径、命令、端口、模型、已有数据>
- 目标：<可验收的一句话>
- 范围：<做什么>
- 非目标：<明确不做什么，防止越界>
- 已知事实：<路径 / 命令 / IP / 表名 / 接口，必须是真的>
- 交付物：<文件路径 + 格式要求>
- 验收标准：<可测、可复现，QA 能照着跑>
- 权限与禁止项：<能不能写哪些目录、能不能装东西、能不能动用户桌面>
- 回报格式：<结论 + 证据 + 置信度；失败时报到哪一步、什么报错>
```
## 5. 协作纪律（Agent Teams）

- **任务先建后派**：`team_task_create` 建任务（写清交付物、验收标准、`write_scopes`）→ 再派给某个成员。
  一个任务只有一个属主；同一份文件不要两个属主同时写。
- **依赖显式化**：B 要用 A 的产出，就写 `blocked_by`，不要靠「等一会儿」。
- **不轮询**：等成员用 `wait_agent`（有超时）；醒来看 `list_agents` + `team_task_list` 再决定下一步。
- **阶段门禁由主理人裁决**：成员说「做完了」不等于通过，逐条核对门禁清单。
- **证据先于结论**：任何「已修复 / 已通过 / 已生效」都必须附本次实测的原始输出（命令 + 返回码 + 关键行，
  或截图路径）。跑不出来的，就写 `unverified`。
- **不可逆操作要用户点头**：删数据、改 profile、装插件、重启服务、对外发布。
- **凭据只写位置不写值**。
## 6. 一批任务的收尾（每次都要做）

1. 汇总：通过 / 未通过 / 未开始，各自证据。
2. 未通过的：缺哪一条门禁，谁在跟，什么时候再看。
3. 沉淀：新学到的命令、路径、坑、口径，写进对应角色技能或 `docs/`，不要留在对话里。
4. 下一步：下一阶段的任务书草稿（写清依赖关系）。
